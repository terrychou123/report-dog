# JUDGMENT.md — 判斷力 checklist（弱模型可執行版）

> 每節格式：判準（可觀察的事實）→ 正例 → 反例。
> 用法：遇到節標題描述的情境時，逐條對照，不要憑感覺。

## §1 何時該升級模型（配合 DISPATCH.md §4）

升級訊號（任一成立就升）：
- [ ] 同一子任務已失敗，且失敗原因是「理解錯」而不是「打錯字/路徑錯」
- [ ] 任務需要在 2 個以上合理方案間取捨，且選錯的代價高（資料遺失、對外發佈、安全）
- [ ] 需求本身模糊，需要先「想清楚問題是什麼」才能動手
- [ ] 跨 3 個以上模組追因果鏈的 debug

**正例**：sonnet 兩次都把 `/blog` 500 修在表層（加 try-catch），沒找到連線囤積的根因
→ 帶著兩次的修法與為何無效，升 opus 重新診斷。
**反例**：改 20 個檔案的 import 路徑改錯了一個 → 這是機械錯誤，修正範例後同級重派即可，
升級 opus 是浪費。

## §2 何時算真的完成（宣告「完成」前逐項打勾）

- [ ] 驗收條件逐條核過（沒有驗收條件 = 開工前的失誤，現在補寫再核）
- [ ] `npx tsc --noEmit` 與 `npm run lint` 通過（動了 .ts/.tsx 才需要）
- [ ] 行為改動有實跑證據（dev server 起來、該頁面/該 API 打過、看到預期輸出）——
      「編譯過了」不是行為證據
- [ ] 改到評鑑 SSOT 檔案 → drift check + evaluation:sync 已跑（CLAUDE.md 工作流）
- [ ] 沒有靜默跳過的步驟；跳過的都已寫在回報裡
- [ ] 文件類產出（.md、規格等非程式碼文字）經過 fresh-context read-back（DISPATCH.md §6）；
      程式碼不需要 read-back，用上面的 tsc/lint＋實跑即可

**正例**：「退訂 API 完成：tsc/lint 過，curl 帶有效 token 回 302、過期 token 回 ?ok=0，
skip 了 email 實寄（無測試環境），已標註。」
**反例**：「已完成退訂功能」——沒跑過任何請求，token 過期分支從沒執行過。這叫「寫完」，不叫「完成」。

## §3 何時該停下來問使用者

先明確：**可逆、在原任務範圍內的事不問，直接做**。要問的是：
- [ ] 不可逆或難回復：刪資料、改 DB schema push 到正式庫、`db:seed-templates --force`、
      改 git 歷史、對外發佈（deploy、寄信、發文）
- [ ] 兩種解讀會做出**不同的東西**，且猜錯要重工一半以上
- [ ] 發現任務前提錯誤（要改的東西不存在、規格與現況矛盾）
- [ ] 成本結構改變：做下去要動到原本說好不動的區域
- [ ] 已到重試上限（DISPATCH.md §4）

問的格式：先給自己的建議選項＋理由，再列其他選項。不要只丟問題。

**正例**：「migration 0018 會 drop `leads.note` 欄位，正式庫已有 1,400 筆資料。
建議先備份該欄再跑，或改用軟刪除。要哪個？」
**反例 A（該問沒問）**：直接跑了 drop column 的 migration，事後才報告。
**反例 B（不該問卻問）**：「我可以開始重構這個函數了嗎？」——可逆、在範圍內，直接做。

## §4 方向錯了的訊號（換路，而非重試）

重試 = 同方法再來一次；換路 = 換方法。出現以下任一訊號，**禁止重試**，必須換路或上報：

- [ ] 修 A 壞 B、修 B 壞 A（蹺蹺板）→ 你修的是症狀，不是原因。停手，回去找共同上游
- [ ] 同一個錯誤訊息第 3 次出現 → 你的假設錯了，重新讀錯誤訊息的**每一個字**，列出 3 個新假設
- [ ] 為了讓方案成立，特例（if/switch 分支）越加越多 → 抽象選錯了，考慮換切法
- [ ] 開始想「先 hack 過去之後再改」→ 這是方向錯誤的自白，停下來重估
- [ ] 診斷用的訊號（log、錯誤）跟你的理論對不上，但你想「大概是快取」搪塞 → 對不上就是理論錯

**正例**：blog 500 修了兩次都復發，第三次不再加防呆，而是往上游查到「列表頁撈全文 content
→ 無快取 → 連線囤積」的因果鏈，一次修根因。
**反例**：cacheComponents 與 revalidate 衝突報錯，反覆調 revalidate 數值試了 5 種——
錯誤訊息明說兩者互斥，任何數值都不會過。

## §5 品質底線怎麼驗（最低標準，不是理想標準）

| 產出 | 底線（全過才算合格） |
|---|---|
| 程式碼 | tsc + lint 綠；有實跑證據；沒有註解掉的殘骸與 console.log 遺留；符合 CLAUDE.md 架構不變量 |
| 評鑑/法規內容 | 每個條號、項目數、年度都能對回 `*-evaluation` skill；**一個都對不上就整篇擋下** |
| 產品文案 | 提到的功能在 codebase 裡真的存在（去 components/app 下確認），禁用「自動生成」「智能適配」等未驗證詞 |
| Blog/SEO | title 25–30 字、description 70–80 字；SVG 遵守 svg-illustration skill；TOC/TLDR 完整（audit:blog） |
| 文件/handbook | fresh-context read-back 能正確轉述；無互相矛盾的規則 |

**品味與模糊題的誠實條款**：以上驗的是底線，驗不了「好不好看」「文章有沒有說服力」這類品味題。
遇到品味題：(1) 先對照 DESIGN.md / 寫作 skill 的明文規則；(2) 規則沒涵蓋的部分，產 2–3 個變體
讓使用者選，**不要自己拍板**；(3) 明說「這部分是品味判斷，我的信心低」。裝有把握是最貴的錯誤。
